# Zyrex integration research

Source: `OTP.zip` (`README.md`, `openapi.json`, `errors.json` and example clients). The archive describes revision 14; the actual provider URL and credentials must be supplied by the operator. This document records findings, not a working integration or proof that the provider is currently reachable.

The OpenAPI security schemes specify bearer authentication or `X-API-Key`. Paths relative to `/api/v1`: GET `/balance`, `/services`, `/countries`, `/offers`, `/order/{order_id}`, `/requests/{reference}`; POST `/order`, `/order/{order_id}/cancel`. The contract also includes separate SMM endpoints, outside this initial OTP scope. Catalog ordering and required purchase fields differ across servers; consult the archive for schemas. Prices are IDR; server 2/4/5 quotes expire after 90 seconds, and server 1/3 require their quoted price. Never substitute a client-provided price for a verified offer.

The guide specifies a stable 16–128 character `Idempotency-Key` for one purchase and identical retries, a shared 20 purchases/minute bucket and 180 other requests/minute per key. HTTP 202 may mean an unresolved purchase; persist the `reservation_ref` and query `/requests/{reference}`. Timeouts and some server errors can also be uncertain. Do not automatically make a replacement purchase or generate a new key. A successful HTTP status is not necessarily a successful business operation. Poll order status at 5–10 second intervals with a deadline, stopping on OTP or terminal status. Cancellation is subject to provider rules including a three-minute minimum and is not a refund until the provider confirms it. Provider webhooks are not documented.

Future adapter must validate response bodies and business status, constrain base URL to operator configuration, prevent redirects, apply connection/response timeouts, redact logs, honor rate limits and only retry safe reads with bounded backoff. It must not expose API keys or OTPs to logs. A server-only read-only adapter in `src/provider/zyrex.mjs` supports balance, services, countries and offers; mock tests cover basic success and error handling. It is not wired to the public server and has not been verified against a live provider. The adapter also offers server-only documented order and reservation status reads, tested only with mocks; their payloads may contain OTP values and must never be logged. There is no provider health check, order creation, cancellation, status synchronization or live purchase. Before implementation review the complete supplied contract and error catalog again, verify its version with the provider, and confirm ambiguous response shapes and retention requirements.
